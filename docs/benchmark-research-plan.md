# Программа экспериментов MetaRescue

Источник: весь приложенный текст (538 строк) и доступная ветка; [карта источников](sources/README.md). Это общая программа, а не перечень уже реализованных функций v0.2/v0.3.

## 1. Соперники

Разведка: Random Search как контроль, Sweep/Lawnmower как обязательная простая стратегия, Greedy, Frontier-based как сильная классическая эвристика, Scout NSGA-II.

Эвакуация: Nearest Robot, Greedy Scheduling, Local Search, Rescue NSGA-II, опционально настоящий OR-Tools. Auction/min-cost assignment сохраняется как дополнительная идея из раннего обсуждения. Для OR-Tools сначала согласуются те же вместимость, энергия, временные ограничения, возможность пропуска, приоритеты и критерий выбора. Название библиотеки не гарантирует эквивалентность постановок.

Полная миссия: пять действующих связок перечислены в `current-concept.md`. Дополнительно исследовать Frontier + OR-Tools, если адаптация решателя соответствует общей модели. Во всех связках один и тот же метауровень; его включение — отдельный фактор эксперимента.

SPEA2 и MOEA/D — возможные будущие многокритериальные соперники при наличии проверенных реализаций и адаптеров. Это не утверждение, что нужные реализации уже включены в проект или доступны в любой версии pymoo.

## 2. Семейства сценариев

| Семейство из обсуждения | Содержание | Что проверяет |
|---|---|---|
| S1 открытая местность | Мало препятствий, равномерные цели | Базовую эффективность |
| S2 разрушенный город | Здания, завалы, узкие проходы | Наземные пути и распределение |
| S3 скопления | Несколько концентраций людей, неизвестных планировщику | Приоритизацию разведки |
| S4 дефицит ресурсов | Меньше энергии и/или эвакуаторов | Отбор выполнимых задач |
| S5 неполная информация | Пропуски сенсора, неточная карта | Устойчивость знаний и повторную разведку |
| S6 динамическая катастрофа | Новые завалы, отказ агента, потенциальная потеря связи | Реакцию и перепланирование |

Фактическая v0.2 называет S6 «Отказ робота»; полноценная динамическая катастрофа — расширение этого исследовательского семейства. Вероятностные события v0.3 являются отдельными параметрами, чтобы не смешать влияние базового рельефа и возмущений. Потеря связи пока только будущая часть полной системы.

В раннем плане предложены уровни: 5/20/50 людей, 2/3/5 дронов, 2/4/8 эвакуаторов, карты 50×50 / 100×100 / 200×200. Это **исследовательские ориентиры**, не уже поддерживаемые диапазоны v0.2 (25–65 с дискретным набором). Первые прогоны делать в допустимых размерах, расширение валидатора и производительности проверять отдельно. Отдельная серия скорости планирования: 5, 10, 20, 30, 50, 100 целей; 100 также превышает текущий лимит v0.2.

Для проверки масштаба нужны два режима: (а) сохранять время/энергию и менять только размер/число задач; (б) масштабировать ресурсы вместе с картой, как v0.2. Эти результаты нельзя объединять в один график без обозначения режима.

## 3. Единый экспериментальный протокол

1. Зафиксировать версии кода, модели, метрики, параметры рельефа, популяцию, ресурсы, горизонты, вероятности и правила сенсоров.
2. Для каждого семейства создать **30 независимых карт**. Для стохастических оптимизаторов на каждой карте выполнить **3 независимых запуска алгоритма**. Seed мира и seed оптимизатора хранить раздельно.
3. Всем методам дать одинаковые карту/энергию/способности/маршрутизатор/сенсор/исполнитель/охранные проверки и внешнюю ленту событий. Доступное знание определяется фактическими наблюдениями, без чтения скрытой истины.
4. Установить одинаковый предел реального времени одного перепланирования; отдельно сохранить число оценок. Дополнительно провести сравнение при одинаковом числе оценок — это другой режим, не гарантия одинакового CPU.
5. Отключить кэш готовых результатов для измерительных прогонов; кэш путей/оценок разрешён как явно заданный вариант алгоритма. Не считать прежнее время из ответа HTTP новым измерением.
6. Сохранять сырые записи каждого запуска и причины частичного результата, отказов, перепланирований и превышений бюджета. Не выбирать удачный seed после просмотра результатов.
7. Сравнивать парно по общей карте/ленте: среднее, стандартное отклонение, медиана и интервалы разницы. Три запуска одного мира не выдавать за три независимые карты; агрегировать с учётом вложенной структуры повторов.
8. Основные выводы делать по физическим метрикам и нарушениям, а не только по одному составному индексу. Указывать размер выборки, оборудование и ограничения постановки.

Модельное время и CPU различаются. Минимальный offline-тест измеряет их отдельно. Для online-применения дополнительно нужен режим, где задержка планирования действительно задерживает команды; иначе нельзя утверждать, что алгоритм с долгим поиском так же пригоден для реального управления.

## 4. Метрики результата

**Разведка:** первый обнаруженный, время достижения 50% и 90% полной популяции, доля найденных к горизонту, обследованная площадь/сектора, повторное обследование, энергия дронов и CPU плана. Если порог не достигнут — `null`/не достигнут, не нулевое время.

**Эвакуация:** своевременно доставленные и их доля, сумма спасённых приоритетов отдельно, первая/последняя доставка, среднее время от старта, от обнаружения и от начала рейса — с разными названиями; время окончания активности и успешного выполнения всей миссии; энергия и CPU.

**Вся система:** те же результаты, плюс отказы, остановки, нарушения, качество переключений сценариев, задержки реакции, восстановление выполнения и полнота причин в журнале. Для полного проекта дополнительно нужны переносимость и совместимость с независимой средой.

Энергия — накопленный фактический расход всех действующих типов агентов. В модели без пополнения разность начального/конечного заряда подходит; при подзарядке требуется баланс `расход = начальный + полученный заряд − конечный` с учётом потерь/ограничений принятого заряда. В v0.2 зарядки нет. Ретрансляторы включаются в баланс только после появления в реализованной модели.

Сравнивать энергию также при одинаковом числе спасённых: алгоритм, ничего не спасший, не получает преимущество за бездействие.

## 5. Качество многокритериального поиска

NSGA-II возвращает множество компромиссов. Сохранять фронт и правило выбора исполняемого плана, а не только выбранный маршрут.

- **Hypervolume (HV):** фиксированные направления целей, нормировка и опорная точка до эксперимента. Сравнение имеет смысл для одной постановки; произвольная опорная точка может изменить вывод.
- **IGD+:** расстояние до эталонного множества. Истинный фронт на больших задачах неизвестен; объединение недоминируемых результатов разных методов/длинных запусков допустимо только с явной маркировкой «приближённый эталон».
- На малых задачах построить точный/переборный ориентир, где вычислительно возможно.
- Фронты разных online-раундов с разными людьми, ресурсами и временем **не объединять в один якобы общий фронт**. Сравнивать одинаковые контрольные снимки задачи либо оценивать динамические показатели отдельно.

HV/IGD+ в текущей v0.2 не вычисляются. Использование pymoo — возможный способ реализации и проверки, но не обязательная зависимость основного локального приложения.

## 6. Контрольные отключения и дополнительные идеи

Сохранены все предложенные в обсуждении сравнения:

- NSGA-II против Greedy по результату и времени вычисления.
- NSGA-II против адаптированного OR-Tools с теми же ограничениями.
- Обычный NSGA-II против версии с кэшем путей/оценок и повторным использованием популяции/плана.
- Два NSGA-II вместе против улучшения только разведки или только эвакуации.
- Система с метасценарным перепланированием против системы без него.
- Фиксированный сценарий без переключения и локальное реактивное управление без явного метауровня — отдельные контрольные варианты для сопоставления с принятой спецификацией проекта. Их соответствие официальным критериям проверяется по актуальному ТЗ, не только по тексту чата.
- Устойчивость при отказах, корректность переключений, переносимость и полнота журналов отдельно от качества маршрутов.

Оптимизация порядка задач/назначений — генетический алгоритм, **не генетическое программирование**. GP/структурный синтез может позже изменять исполняемую стратегию кооперации; такой механизм должен иметь собственную семантику и тесты, а не другое название того же маршрутизатора. Аукцион/игровые методы распределения — также отдельные возможные политики, не уже реализованный компонент.

## 7. Артефакты и порядок внедрения

Для каждого прогона: `run_id`, версии кода/модели/метрики, все seed, конфигурация, ID/хэш событий, метод/бюджет, параметры оптимизатора, публичные наблюдения и решения, подтверждённые действия, результаты, нарушения и времена. Сохранить CSV для сравнения и JSON/журнал для проверки причин.

Графики: отдельные кривые людей по времени с общей шкалой; фронты Парето; CPU в зависимости от числа целей и агентов; распределение результатов по seed. Числа 0/5/10/... и кривые из строк 403–431 приложенного контекста были **иллюстративными**, их нельзя выдавать за выполненный эксперимент.

Раннее предложение `benchmarks/scenarios.py`, `baselines/`, `benchmark_scout.py`, `benchmark_rescue.py`, `benchmark_full.py`, `metrics.py`, `plots.py`, `run_all.py` описывало разделение ответственности. После появления v0.2 сохраняем её фактическую структуру; переименование под раннюю схему само по себе не улучшает исследование и не требуется.

Практический порядок: единый сценарий/протокол → работающие простые базовые политики → проверка разведывательного NSGA-II → сильный эвакуационный ориентир → Rescue NSGA-II → полная миссия с динамикой → 3D и метауровень → расширенная статистика. Несколько seed пригодны для smoke; план 30×3 и разнообразные условия нужны для убедительной защиты результатов.
