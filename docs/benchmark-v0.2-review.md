Основная версия использует стандартную библиотеку Python 3.10+. В `requirements-optional.txt` указан `ortools>=9.10,<10`. Отсутствие OR-Tools не препятствует основным трём страницам.

Карта: 25/35/45/55/65 клеток на сторону, сектор 5×5, 1 клетка = 10 м. Дроны 1–10, эвакуаторы 1–12, люди 3–80. Горизонт и батареи масштабируются с размером карты. Поэтому увеличение карты в v0.2 одновременно меняет условия по времени и энергии; это не чистый эксперимент на одном факторе масштаба.

Типы клеток: `0` обычная поверхность, `1` непроходимое препятствие, `2` труднопроходимая поверхность с коэффициентом 1.45, `3` ещё один непроходимый тип. В коде у типа 3 отдельная физическая семантика не определена; называть его полноценным затоплением пока нельзя.

Сценарии S1–S6: открытая местность, город, скопления, дефицит энергии, пропуски сенсора, отказ эвакуатора. S6 создаёт отказ на `95 × размер/25` секунде; изменение ландшафта не выполняется. Отказ исполняется в общей миссии, не на двух автономных страницах.

Разведка не использует скрытые координаты в функции качества. Дрон обследует сектор целиком из его центра. Эвакуатор берёт одного человека, возвращается на базу; зарядки нет. Проверяется резерв 10% батареи. Для дрона это процентный резерв, а не доказанный расчёт энергии безопасного возвращения; обратный полёт на базу в разведывательной трассе отсутствует.

## Формулы и смысл метрик

В v0.2 баллы рассчитываются в `static/app.js`, не являются официальной оценкой хакатона:

```text
P = число результатов / N
T = сумма max(0, 1 - время результата / H) / N
E = P × max(0, 1 - расход / (0.9 × исходная энергия команды))
D = число обнаружений / N
scout:   65P + 25T + 10E
rescue:  70P + 20T + 10E
mission: 60P + 15D + 15T + 10E
```

Результат — обнаружение на первой странице и доставка на остальных. При отсутствии результата экономия не даёт баллы. Эти веса не означают строгую лексикографическую гарантию «один дополнительный человек важнее всех бонусов»: при большом N небольшое изменение числа людей может быть перекрыто скоростью/энергией. Если нужна такая гарантия, её вводить отдельной версией метрики, сохранив старые результаты.

`finished_at` — последняя запланированная активность с ограничением горизонтом, а не «все спасены». В интерфейсе этот итоговый показатель виден даже при просмотре раннего модельного времени; подпись об этом есть. `last_rescue` — последняя успешная доставка. Средний рейс — среднее «передача минус отправление» по завершённым рейсам. Темп — число доставок × 60 / время последней доставки. Это не равно «время от обнаружения до доставки» и не равно «текущее время / число спасённых».

У Rescue NSGA-II первая цель — **сумма приоритетов не спасённых**, затем взвешенные сроки и энергия. В v0.2 нет индивидуальных медицинских дедлайнов: ограничение — общий горизонт. Число людей и сумма приоритетов — разные критерии; это требуется явно сохранять в отчётах и согласовать при доработке, не менять молча.

## Замечания для следующей версии

1. **Динамика не реализована.** `World.route` кэшируется только по началу/концу. Для изменяемой карты потребуется инвалидировать кэш и изолировать состояния пяти запусков.
2. **Локальное движение по рельефу.** `trip()` правильно использует взвешенную длину пути для общей длительности. Но `mission_segments.move()` распределяет время/энергию между всеми соседними рёбрами одинаково (`1+0.5*(a!=b)`), независимо от их реального рельефа. Визуальная локальная скорость не соответствует стоимости конкретной клетки; при динамике это нужно исправить.
3. **Положение груза при отказе.** В `run_mission()` отменённый рейс возвращает задачу к исходному `person_by_id`, даже если человек уже перевозился. Для физически корректной динамики требуется сохранить фактическую позицию груза у отказавшего робота, а не начинать повторный рейс от исходной точки.
4. **Повторное обнаружение S5.** Пропуск сенсора определён только seed и ID человека. При повторном обследовании тот же человек останется пропущенным. Для дыма и меняющейся видимости нужен зависящий от времени/наблюдения сенсор и повторные посещения.
5. **OR-Tools fallback.** При отсутствии пакета панель честно не добавляется. Но если установленный решатель не вернул допустимого решения, `ortools_plan()` возвращает жадный план со статусом `no_feasible_solver_solution`. Обычная панель этот статус не раскрывает. До строгого сравнения показывать статус/fallback и не учитывать эвристику как результат CP-SAT.
6. **Согласование целей CP-SAT.** Большие коэффициенты в суммарной целевой функции сами по себе не доказывают лексикографическое превосходство спасения на всех разрешённых размерах. Нужна проверка границ коэффициентов либо последовательные этапы оптимизации, плюс сопоставимые приоритеты и критерии выбора с NSGA-II.
7. **Бюджеты и измерения.** NSGA-II, локальный поиск и CP-SAT имеют разные бюджеты. `run_collection` кэширует результат вместе с измеренным CPU; повтор запроса может показать старое время, а не новый замер. Для исследования нужен отдельный некэшированный режим и одинаковые бюджеты.
8. **S1–S6 не покрывают весь исследовательский план.** Потеря связи, динамические разрушения, полноценные метасценарные операции, HV/IGD+, SPEA2/MOEA/D и независимые seed оптимизатора не реализованы. Пакетный CLI не принимает размеры/парк из UI, только число людей, seed, сценарий и режим.

Это замечания к известной базе, а не выполненные исправления: исходный импорт намеренно оставлен побайтово неизменным. Ветка v0.3 должна проверяться на эти пункты после получения её кода.

## Выполненные проверки

Из корня репозитория:

```powershell
python -B -X utf8 -m unittest discover -s "benchmarks/metarescue-v0.2/main part/tests" -v
```

Фактически: **16/16 успешно**, Python 3.14.3, 3.239 с. Это алгоритмические/конфигурационные тесты; сам по себе этот набор не проверяет весь браузерный UX, установку OR-Tools или сетевой транспорт.

Дополнительно выполнен вызов `server.run_collection` для трёх режимов на seed 2026, urban, 25×25, 16 людей, 3 дронах, 4 эвакуаторах. Получены 5/4/5 результатов. Все разведывательные методы нашли 16; offline-эвакуация дала 13/13/13/14 доставок в порядке nearest/greedy/local/nsga2; в полной миссии все пять связок доставили 12. Это один smoke-пример, не статистическое доказательство превосходства. Время формирования коллекций на текущем ПК: 0.238 / 0.272 / 2.204 с соответственно.

В отдельном фактическом HTTP-smoke временный сервер слушал свободный loopback-порт: `/api/health`, `/scout`, `/rescue`, `/mission` и `/api/simulation?mode=mission&seed=2026&people=8&scenario=urban&map_size=25&scouts=2&rescuers=3` вернули **200**. Сервер после проверки остановлен. JavaScript прошёл `node --check`. Повторная сверка манифеста: 19/19 файлов сохранили исходные SHA-256. `git diff --check` не нашёл ошибок (предупреждение Git о будущем CRLF у README не является ошибкой проверки).

Не проверено: реальное оборудование, физиологическая достоверность, перенос в 3D, runtime-интеграция с нормативным контроллером и опциональный OR-Tools. Заявления старого чата о проверках не заменяют эти фактические результаты.
